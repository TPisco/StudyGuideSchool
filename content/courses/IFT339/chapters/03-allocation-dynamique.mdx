## 1. Rappel : blocs, durée de vie, portée

La programmation est **structurée en blocs**. Un **bloc** est une partie du
code délimitée par deux accolades.

Deux notions se ressemblent et ne coïncident pas :

- la **durée de vie** d'un objet va de sa **déclaration** (allocation de
  mémoire) à la **fermeture du bloc** dans lequel il est déclaré (libération) ;
- la **portée** d'un objet est l'ensemble des parties du code **où l'objet est
  accessible**.

```cpp
{  //Bloc A
   int i = 0;
   ...
   { //Bloc B
   ...
   }
   ...
   { //Bloc C
   ...
   }
   ...
}
```

Il est possible de **donner un nom à une portée** avec le mot-clé
`namespace`.

## 2. Le modèle de la pile d'exécution

### 2.1 Le principe

À l'**ouverture** d'un bloc : allocation de l'espace mémoire des variables
locales — **sauf pour les paramètres passés par référence**.

À la **fermeture** : libération de l'espace alloué à l'ouverture — **sauf pour
les variables locales retournées par référence**.

Chaque bloc ajoute un **cadre de pile** contenant :

- les **variables locales** ;
- les **paramètres** ;
- le **retour**.

<Mermaid caption="Ouverture et fermeture des cadres pour trois blocs imbriqués (diapositives 5 et 6)." chart={`

<Callout type="note" title="« sauf retour »">
Les diapositives répètent cette mention à chaque fermeture. C'est elle qui
explique comment une valeur survit à la disparition du cadre qui l'a produite —
et pourquoi un **retour par référence** vers une variable locale est dangereux :
la valeur de retour est conservée, la variable locale non.
</Callout>

### 2.2 Pourquoi ce modèle : la récursivité

Le cours le présente comme « particulièrement adapté à la gestion de la
récursivité ».

```cpp
int factorielle(int n)
{
    int fact = 0;
    if(n == 0)
        fact = 1
    else
        fact = n * factorielle(n - 1);
    return fact;
}
```

Chaque appel ouvre **son propre cadre**, avec sa propre copie de `n` et de
`fact`. Pour `factorielle(2)` :

| Étape | Pile (du sommet vers la base) |
| --- | --- |
| Ouverture de `factorielle(2)` | `fact : 2 * factorielle(1)` · `n : 2` |
| Ouverture de `factorielle(1)` | `fact : 1 * factorielle(0)` · `n : 1` — puis le cadre de 2 |
| Ouverture de `factorielle(0)` | `fact : 1` · `n : 0` — puis les cadres de 1 et de 2 |
| Fermeture de `factorielle(0)` | retourne 1 ; le cadre disparaît **sauf le retour** |
| Fermeture de `factorielle(1)` | `fact : 1 * 1 = 1` ; retourne 1 |
| Fermeture de `factorielle(2)` | `fact : 2 * 1 = 2` ; retourne 2 |

<Callout type="misconception" title="Erreur classique">
Croire que `n` est une seule variable qui « descend » au fil des appels. Il y a
**autant de `n` que de cadres**, vivants simultanément. C'est exactement
pourquoi une récursion de profondeur $p$ consomme $\Theta(p)$ de mémoire, et
pourquoi une récursion sans cas de base finit par épuiser la pile.
</Callout>

## 3. Passages de paramètres et retours — vus côté mémoire

Le chapitre 2 donnait la syntaxe ; celui-ci donne l'effet mémoire.

| | Espace mémoire | Accès / contrainte |
| --- | --- | --- |
| **Paramètre par référence** | **aucun espace alloué**, identificateur différent | **lvalue seulement** |
| **Paramètre par valeur** | **nouvel espace alloué**, copie de la valeur du paramètre effectif | **rvalue possible** ; mémoire du paramètre effectif **non accessible** |
| **Retour par référence** | mémoire **non désallouée**, accessible après la sortie | doit **exister avant le début du bloc** ; **lvalue seulement** |
| **Retour par valeur** | nouvel espace alloué automatiquement à la fermeture du bloc ; l'espace local est désalloué | la **copie** est accessible ; **rvalue possible** |

## 4. Allocation automatique contre allocation dynamique

### 4.1 L'allocation automatique

Elle est **automatique et implicite** :

- crée des objets **à la déclaration** — **aucune initialisation** ;
- supprime les objets **à la fin** — **aucun nettoyage** ;
- libère **uniquement** la mémoire allouée automatiquement.

### 4.2 L'allocation dynamique

Elle est **explicite** :

- crée des objets et **retourne des pointeurs** vers eux ;
- **aucune initialisation** du contenu pointé ;
- **aucun identificateur** pour l'objet pointé.

```cpp
Type *ptr = new Type;
```

L'opérateur `new` fait **appel au constructeur** de l'objet.

### 4.3 Accéder à l'objet

L'objet pointé **n'a pas de nom** : la seule façon d'y accéder est de
**déréférencer**.

| Opération | Opérateur | Sur quoi |
| --- | --- | --- |
| Déréférencement | `*` | sur le **pointeur** — retourne un objet par référence, protégé ou non |
| Projection sur un membre | `.` | sur l'**objet** — accès à la valeur des attributs |
| Déréférencement **et** projection | `->` | sur le **pointeur** |

Les notes donnent l'équivalence :

```cpp
ptr->id   // equivalent a   *ptr.id
```

### 4.4 Libérer

L'opérateur `delete` **appelle le destructeur** de l'objet pointé, `~Type()`.

<Callout type="warning" title="Deux choses que delete ne fait pas">
Après `delete ptr;` **le pointeur existe toujours** — il désigne une mémoire
qui n'est plus à nous. Et les objets créés dynamiquement sont **à supprimer
explicitement par l'usager** : rien ne le fera à sa place, contrairement à
l'allocation automatique.
</Callout>

## 5. La sémantique de déplacement

### 5.1 Le problème

Les retours et paramètres **par valeur** sont des **rvalues** : ils génèrent des
**copies temporaires**. Or la source des données, avant la copie :

- est **non accessible** ;
- **disparaît aussitôt utilisée**.

D'où « mémoire et traitement inutiles » — **surtout pour les conteneurs**.

### 5.2 L'idée

Plutôt qu'une copie profonde, faire une **copie de surface** qui :

- **détruit la référence** vers l'objet d'origine ;
- ne conserve que la **« nouvelle » référence**.

Les notes sont prudentes sur le vocabulaire : cela « s'apparente à un
déplacement de la mémoire (**mais pas vraiment**) ».

### 5.3 La référence vers rvalue

Une **référence vers un objet temporaire** se note avec le symbole `&&`. Elle
permet un **copieur et un affectateur de rvalue**, qui **évitent les copies
profondes**.

```cpp
Type(const Type&);              // constructeur par copie
Type(Type &&);                  // constructeur par mouvement
Type& operator=( const Type &); // affectation par copie
Type& operator=( Type &&);      // affectation par mouvement
```

<Callout type="warning" title="Les signatures ne suffisent pas">
Les notes insistent : ces quatre signatures sont **requises**, mais « la copie
ou l'affectation doivent être **codées** selon la signature (copie profonde ou
de surface) ». Déclarer un constructeur par mouvement qui fait une copie
profonde compile parfaitement et n'apporte rien.
</Callout>

## 6. Mettre le modèle à l'épreuve

L'exercice « récursion mystère » fourni avec le cours demande de détailler la
pile d'exécution pour `mystere(3)` :

```cpp
int mystere(int n){
  if (n==1)
    return 1;
  if (n%2 == 0)
    return mystere(n/2);
  else
    return mystere(3*n+1);
}
```

<Callout type="note" title="Pourquoi cet exemple plutôt que factorielle">
Parce que la suite des appels n'est pas monotone : elle **monte** avant de
descendre. On ne peut pas deviner la profondeur en regardant l'argument
initial, ce qui oblige à dérouler réellement les cadres au lieu d'appliquer un
schéma appris. C'est l'exercice du chapitre — il est repris dans les exercices
de cette page.
</Callout>
