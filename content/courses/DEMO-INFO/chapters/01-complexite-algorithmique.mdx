## 1. Pourquoi ne pas simplement chronométrer ?

Mesurer un algorithme avec un chronomètre donne un nombre qui dépend de la
machine, du langage, du compilateur et de la charge du système. Le même
programme peut être deux fois plus rapide sur un autre portable sans qu'une
seule ligne ait changé.

L'analyse de complexité répond à une autre question : **comment le coût
évolue-t-il quand la taille de l'entrée augmente ?** C'est une propriété de
l'algorithme, pas de la machine.

<Callout type="note" title="La question à se poser">
Si je double la taille de l'entrée, le temps double-t-il, quadruple-t-il, ou
augmente-t-il à peine ? C'est la seule question à laquelle la complexité
asymptotique répond — et c'est celle qui décide si un programme tient sur des
données réelles.
</Callout>

## 2. Le modèle de coût : les opérations élémentaires

On choisit un **modèle de coût** : on décide quelles opérations comptent pour
1, puis on compte combien de fois elles sont exécutées en fonction de $n$, la
taille de l'entrée.

Sont comptées pour 1 (coût constant) :

- une affectation ;
- une comparaison ;
- une opération arithmétique ;
- un accès à une case de tableau par son indice.

```python
def somme(tableau):          # n = len(tableau)
    total = 0                # 1 affectation
    for x in tableau:        # n itérations
        total = total + x    # 1 addition + 1 affectation, n fois
    return total             # 1 retour
```

Le compte exact vaut $T(n) = 2n + 2$ opérations. Ce «&nbsp;2&nbsp;» devant $n$
et cette constante $+2$ dépendent de la façon de compter ; c'est précisément
pour s'en débarrasser qu'on introduit la notation asymptotique.

## 3. Notation asymptotique : O, Ω et Θ

### 3.1 Définitions

Soient $f$ et $g$ deux fonctions de $\mathbb{N}$ vers $\mathbb{R}^{+}$.

$$
f(n) = O\bigl(g(n)\bigr) \iff \exists\, c > 0,\; \exists\, n_0 \in \mathbb{N},\; \forall n \ge n_0 : f(n) \le c \cdot g(n)
$$

$$
f(n) = \Omega\bigl(g(n)\bigr) \iff \exists\, c > 0,\; \exists\, n_0 \in \mathbb{N},\; \forall n \ge n_0 : f(n) \ge c \cdot g(n)
$$

$$
f(n) = \Theta\bigl(g(n)\bigr) \iff f(n) = O\bigl(g(n)\bigr) \text{ et } f(n) = \Omega\bigl(g(n)\bigr)
$$

En français :

- $O$ est une **borne supérieure** : « ne croît pas plus vite que ».
- $\Omega$ est une **borne inférieure** : « croît au moins aussi vite que ».
- $\Theta$ est un **encadrement** : « croît exactement comme ».

<Callout type="misconception" title="Erreur classique">
Écrire $O$ alors qu'on veut dire $\Theta$. Dire « le tri par insertion est en
$O(n^2)$ » est **vrai mais faible** : il est aussi en $O(n^3)$, et même en
$O(2^n)$, puisque $O$ n'est qu'une borne supérieure. Pour affirmer que c'est
sa vitesse réelle de croissance dans le pire cas, il faut écrire $\Theta(n^2)$.
</Callout>

### 3.2 Les deux constantes qui disparaissent

Deux règles suffisent en pratique :

1. **On ignore les facteurs constants** : $2n+2$ et $100n$ sont tous deux $\Theta(n)$.
2. **On ne garde que le terme dominant** : $3n^2 + 50n + 900$ est $\Theta(n^2)$.

La raison est visible sur les valeurs : pour $n = 1000$, le terme $3n^2$ vaut
$3\,000\,000$ tandis que $50n + 900$ vaut $50\,900$, soit moins de 2 % du total.

## 5. Meilleur cas, pire cas, cas moyen

Pour une même taille $n$, deux entrées différentes peuvent coûter des temps
très différents. La recherche séquentielle en est l'exemple canonique.

```python
def recherche_sequentielle(tableau, cible):
    for i in range(len(tableau)):
        if tableau[i] == cible:
            return i
    return -1
```

- **Meilleur cas** : la cible est en position 0 → 1 comparaison → $\Theta(1)$.
- **Pire cas** : la cible est absente → $n$ comparaisons → $\Theta(n)$.
- **Cas moyen** (cible présente, position uniforme) : en moyenne
  $\frac{n+1}{2}$ comparaisons → $\Theta(n)$.

<Callout type="warning" title="Lequel utiliser ?">
Par défaut, on annonce le **pire cas** : c'est la seule garantie. Le cas moyen
demande une hypothèse sur la distribution des entrées, et cette hypothèse est
souvent fausse en pratique. Le meilleur cas ne sert qu'à montrer qu'un
algorithme est parfois rapide — il ne garantit rien.
</Callout>

## 6. Exemple travaillé : boucles imbriquées

```python
def compte_paires(tableau):
    n = len(tableau)
    paires = 0
    for i in range(n):            #  n itérations
        for j in range(i + 1, n): #  (n-1-i) itérations
            if tableau[i] == tableau[j]:
                paires += 1
    return paires
```

La boucle interne ne fait pas $n$ tours : elle en fait $n-1-i$. Le nombre total
de comparaisons est donc

$$
\sum_{i=0}^{n-1} (n - 1 - i) = \sum_{k=0}^{n-1} k = \frac{n(n-1)}{2}
$$

soit $\Theta(n^2)$.

<Callout type="misconception" title="Erreur classique">
Conclure $\Theta(n^2)$ « parce qu'il y a deux boucles imbriquées » est un
réflexe qui marche souvent et qui trompe parfois. Si la boucle interne était
`for j in range(3)`, le coût serait $\Theta(n)$. **Il faut compter les tours de
la boucle interne, pas les niveaux d'imbrication.**
</Callout>

## 7. Exemple travaillé : un algorithme récursif

La recherche dichotomique exige un tableau **trié**. À chaque étape, elle
élimine la moitié de l'espace de recherche.

<Mermaid caption="Recherche dichotomique — une itération élimine la moitié restante." chart={`
flowchart TD
    A["debut = 0, fin = n-1"] --> B{"debut <= fin ?"}
    B -- non --> E["retourner -1<br/>(absent)"]
    B -- oui --> C["milieu = (debut + fin) / 2"]
    C --> D{"comparer<br/>tableau[milieu] et cible"}
    D -- "egal" --> F["retourner milieu"]
    D -- "tableau[milieu] < cible" --> G["debut = milieu + 1"]
    D -- "tableau[milieu] > cible" --> H["fin = milieu - 1"]
    G --> B
    H --> B
`} />

```python
def dichotomie(tableau, cible):
    debut, fin = 0, len(tableau) - 1
    while debut <= fin:
        milieu = (debut + fin) // 2
        if tableau[milieu] == cible:
            return milieu
        elif tableau[milieu] < cible:
            debut = milieu + 1
        else:
            fin = milieu - 1
    return -1
```

**Analyse.** Soit $T(n)$ le nombre de comparaisons dans le pire cas sur un
tableau de taille $n$. Chaque tour fait une comparaison et divise la taille par
deux :

$$
T(n) = T\!\left(\frac{n}{2}\right) + 1, \qquad T(1) = 1
$$

En déroulant : $T(n) = T(n/2^k) + k$. La récursion s'arrête quand
$n/2^k = 1$, c'est-à-dire $k = \log_2 n$. Donc

$$
T(n) = \Theta(\log_2 n) = \Theta(\log n)
$$

<Callout type="note" title="Pourquoi la base du logarithme ne s'écrit pas">
$\log_2 n$ et $\log_{10} n$ ne diffèrent que d'un facteur constant
($\log_2 n = \log_{10} n / \log_{10} 2$). Comme les constantes disparaissent en
notation asymptotique, on écrit simplement $\Theta(\log n)$.
</Callout>

Concrètement : sur un tableau d'un million d'éléments, la recherche séquentielle
fait jusqu'à 1 000 000 comparaisons, la dichotomie environ 20.

## 8. Méthode de travail

<Mermaid caption="La marche à suivre pour analyser un fragment de code." chart={`
flowchart LR
    A["Identifier n<br/>(la taille de l'entree)"] --> B["Reperer l'operation<br/>dominante"]
    B --> C["Compter ses executions<br/>en fonction de n"]
    C --> D["Simplifier :<br/>terme dominant seul"]
    D --> E["Exprimer en Theta<br/>(ou O si borne seule)"]
`} />

1. **Nommer $n$.** Longueur de la liste ? Nombre de bits ? Nombre de sommets ?
   Une complexité sans $n$ défini ne veut rien dire.
2. **Trouver l'opération dominante** — celle qui s'exécute le plus souvent.
3. **Compter** ses exécutions, en sommant sur les boucles.
4. **Simplifier** : terme dominant, constantes jetées.
5. **Écrire** le résultat en $\Theta$ si le comptage est exact, en $O$ si on n'a
   qu'une majoration.
